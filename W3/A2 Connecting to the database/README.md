# Task API With SQLite Persistence

This project is a FastAPI CRUD API for managing tasks. It started as an in-memory task API in Week 2, then was upgraded in Week 3 so task data is stored in a real SQLite database.

The API endpoints stayed the same, but the storage changed:

```text
Before: FastAPI -> Python list in memory
Now:    FastAPI -> SQLite database file
```

That means tasks now survive when the server stops and starts again.

---

## Assignment Goal

The goal of this assignment was to connect the existing CRUD API to a database without changing the API behavior.

The API still supports:

```text
GET    /tasks
GET    /tasks/{task_id}
POST   /tasks
PUT    /tasks/{task_id}
DELETE /tasks/{task_id}
```

The difference is that these endpoints now read and write task rows in SQLite instead of using a temporary Python list.

---

## Why SQLite Was Chosen

SQLite was chosen because it is simple, lightweight, and perfect for a small learning project.

SQLite is useful here because:

- It stores the whole database in one file.
- It does not require a separate database server.
- It works with Python's built-in `sqlite3` module.
- It lets the data survive server restarts.
- It is easy to inspect visually with DB Browser for SQLite.

For this assignment, SQLite gives the most important database lesson without extra setup: data should live outside the running program.

---

## Where The Database Is Stored

The database file is named:

```text
tasks.db
```

It is created automatically in the same folder as `main.py`:

```text
W3/A2 Connecting to the database/tasks.db
```

The app creates the database automatically when it starts. If `tasks.db` does not exist, SQLite creates it. The app also creates the `tasks` table if it is missing.

The database file is ignored by Git with:

```gitignore
*.db
```

That means someone cloning the repository gets a fresh database created automatically when they run the app.

---

## Database Schema

The app creates one table named `tasks`.

```sql
CREATE TABLE IF NOT EXISTS tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    done INTEGER NOT NULL DEFAULT 0
);
```

Columns:

| Column | Type | Purpose |
| --- | --- | --- |
| `id` | `INTEGER PRIMARY KEY AUTOINCREMENT` | Unique task id generated by SQLite |
| `title` | `TEXT NOT NULL` | Task title |
| `done` | `INTEGER NOT NULL DEFAULT 0` | Completion state, stored as `0` or `1` |

SQLite stores booleans as integers:

```text
0 = false
1 = true
```

The API converts those values back to JSON booleans:

```json
{
  "id": 1,
  "title": "Buy milk",
  "done": false
}
```

---

## Automatic Seed Data

On first startup, the app inserts three starter tasks only if the `tasks` table is empty:

```json
[
  {"title": "Buy milk", "done": false},
  {"title": "Walk the dog", "done": true},
  {"title": "Read FastAPI docs", "done": false}
]
```

The app checks the row count first:

```sql
SELECT COUNT(*) AS count FROM tasks;
```

If the count is `0`, it inserts the starter tasks. If tasks already exist, it does not seed again. This prevents duplicate seed data after restarting the server.

## API Endpoints

### `GET /`

Returns basic API information.

```powershell
curl -i http://127.0.0.1:8000/
```

Example response:

```json
{
  "name": "Task API",
  "version": "1.0",
  "endpoints": ["/tasks", "/stats", "/reset"]
}
```

### `GET /health`

Checks whether the API is running.

```powershell
curl -i http://127.0.0.1:8000/health
```

Example response:

```json
{
  "status": "ok"
}
```

### `GET /tasks`

Returns all tasks from SQLite.

```powershell
curl -i http://127.0.0.1:8000/tasks
```

Example response:

```json
[
  {"id": 1, "title": "Buy milk", "done": false},
  {"id": 2, "title": "Walk the dog", "done": true},
  {"id": 3, "title": "Read FastAPI docs", "done": false}
]
```

### `GET /tasks/{task_id}`

Returns one task by id.

```powershell
curl -i http://127.0.0.1:8000/tasks/1
```

Example response:

```json
{
  "id": 1,
  "title": "Buy milk",
  "done": false
}
```

If the task does not exist, the API returns `404`.

```powershell
curl -i http://127.0.0.1:8000/tasks/999
```

### `POST /tasks`

Creates a new task in SQLite.

```powershell
curl -i -X POST "http://127.0.0.1:8000/tasks" -H "Content-Type: application/json" -d "{\"title\":\"Learn SQLite\"}"
```

Example response:

```json
{
  "id": 4,
  "title": "Learn SQLite",
  "done": false
}
```

If the title is empty, the API returns `400`.

### `PUT /tasks/{task_id}`

Updates an existing task in SQLite.

```powershell
curl -i -X PUT "http://127.0.0.1:8000/tasks/1" -H "Content-Type: application/json" -d "{\"title\":\"Buy milk and bread\",\"done\":true}"
```

Example response:

```json
{
  "id": 1,
  "title": "Buy milk and bread",
  "done": true
}
```

If the task does not exist, the API returns `404`.

### `DELETE /tasks/{task_id}`

Deletes a task from SQLite.

```powershell
curl -i -X DELETE "http://127.0.0.1:8000/tasks/1"
```

Successful delete returns:

```text
204 No Content
```

If the task does not exist, the API returns `404`.

### `GET /tasks?done=true`

Filters completed tasks using SQL.

```powershell
curl -i "http://127.0.0.1:8000/tasks?done=true"
```

### `GET /tasks?search=milk`

Searches task titles using SQL `LIKE`.

```powershell
curl -i "http://127.0.0.1:8000/tasks?search=milk"
```

### `GET /stats`

Returns task counts calculated from SQLite.

```powershell
curl -i http://127.0.0.1:8000/stats
```

Example response:

```json
{
  "total": 3,
  "done": 1,
  "open": 2
}
```

### `POST /reset`

Clears the table and inserts the starter tasks again. This is useful while testing.

```powershell
curl -i -X POST http://127.0.0.1:8000/reset
```

Example response:

```json
{
  "message": "Tasks reset to starter data",
  "total": 3
}
```

## Persistence Check

To prove the database works:

1. Start the server.
2. Create a new task with `POST /tasks`.
3. Stop the server.
4. Start the server again.
5. Run `GET /tasks`.

The new task should still be there.

That proves the data is stored in `tasks.db`, not in memory.

## What I Learned

The main lesson from this assignment is that an API and its storage layer are separate.

The client still calls the same endpoints, but the app now stores data in SQLite instead of a Python list. That change makes the API more realistic because data survives after the server restarts.

The most important database safety habit used here is parameterized SQL:

```python
conn.execute("SELECT * FROM tasks WHERE id = ?", (task_id,))
```

The `?` placeholder keeps user input separate from the SQL command, which is safer than building SQL strings manually.
